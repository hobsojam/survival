# The Castle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After the keep, the player finds a line of old stones and spends about 5 in-game years raising a castle around the keep, section by section, ending in a feast and the choice to move in.

**Architecture:** All rules live in a new pure module, `src/game/castle.ts`: one saved `CastleState`, a table of sections and what each still needs, and one action, `castleWork { site }`, that does the next thing a site needs. The scene, prompts and tap targets only read that table. Sprites go in a new `src/art/castleSprites.ts`.

**Tech Stack:** TypeScript, Phaser 3, Vite, Vitest, oxlint.

**Spec:** `docs/superpowers/specs/2026-11-07-castle-design.md`

## Global Constraints

- No new dependencies and no image files. Everything is drawn in code from the existing stone palette.
- Nothing up to the keep's finish changes, in rules or pacing.
- A chore-free, loss-free castle: no fuel, upkeep, timers or decay. Laid stone stays laid, and dug moat stays dug.
- No other people, trading, or anything new to gather or farm.
- Secret: stays out of the README and other player-facing text before it is found. Code carries an `EASTER EGG:` comment, and `AGENTS.md`'s list names it. Nothing about the castle shows before the reveal.
- Copy is plain and warm, not poetic, with no exclamation marks.
- Everything works by tap and by key, and every path works when the survivor is weak (a tired survivor gets `TOO_TIRED_MESSAGE`, never a trap).
- SonarCloud needs 80% on new code and `App.ts` is untested, so logic goes in tested helpers.
- Only one open PR may change the save format.
- Each stage ships as its own PR off `main`, leaving the game whole. Commits end `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. PR bodies end `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
- Every stage ends green on `npx tsc --noEmit`, `npx oxlint --deny-warnings src tests`, `npm test -- --run` and `npm run build`.

## Rulings on the spec

Reading the code turned up four places where the spec can't work as written. These are the plan's decisions, and the user sees them at hand-off.

1. **The feast asks for foods that can be carried, not cooked dishes.** Apple pie, honey cake and stew are eaten the moment they're cooked (`serveDish`). Only bread and roasted hazelnuts are packed. The table asks for `bread`, `roastedHazelnuts`, `honey`, `apple` and `vegetables`.
2. **Goods are counts on the castle, not bag items.** Beams, fittings and hangings are made at camp and then count from anywhere, as the hinges do. This avoids a new bag item and keeps the "no fiddly carrying" rule the keep's door set.
3. **The house keeps working after moving in.** Making the hall home adds a second home. `isAtHome` is true at the house or at the hall, so no choice can strand anyone. The spec's "change their mind" is then a plain toggle.
4. **The offer to move in is a small Camp-tab panel, shown after the first night or climb at the hall door.** The game has no yes/no dialog.

Walls have no collisions, since the game has none today. The hall door by day climbs to the same view as the keep's door.

## Review Focus

1. A cart stuck on the hills when winter comes: laying from it still works, digging at the quarry goes to the bag, and it comes back with the pony in spring.
2. Cart full and bag full at the quarry face: the refusal is the usual full-bag one and spends no energy or dig.
3. A save with the keep finished before this version: upgrades with nothing revealed, first climb after that counts as the first, and it validates at every stage.
4. A hall-home player who is sick, has every camp fire out and is standing at the hall: rest, a warm meal and sleep all work.
5. Moat finished in spring, in summer or just before winter: the fill is right in each, and digging is refused in winter with a clear line.
